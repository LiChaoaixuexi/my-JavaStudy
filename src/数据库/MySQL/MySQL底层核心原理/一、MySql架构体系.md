# MySQL底层原理核心知识点详解文档
## 一、MySQL 架构体系底层逻辑
### （一）分层架构核心职责
1. 连接层：采用TCP/IP协议接收客户端连接，通过用户名密码验证身份，为每个连接分配独立线程（线程池可复用线程）。
2. 服务层：SQL解析器将SQL语句拆解为语法树，优化器基于索引、数据分布生成最优执行计划，查询缓存（8.0后移除）缓存完全匹配的SQL结果。
3. 存储引擎层：通过接口与服务层交互，不同存储引擎独立实现数据存储、读取、事务、锁等核心功能，不依赖其他层。
4. 存储层：将数据文件、日志文件存储在文件系统中，依赖操作系统管理磁盘IO。

### （二）核心组件协作流程
* 总流程概览：
  * ①客户端发起请求（连接/认证/协议）
  * ②SQL 语句接收与协议解析
  * ③解析（Parser）
  * ④预处理（Preprocessor）/语义检查
  * ⑤查询重写/重写规则（可选）
  * ⑥优化器（Optimizer）：生成执行计划（包括代价估算）
  * ⑦执行器（Executor/Query Execution Engine）：按照执行计划访问表/索引
  * ⑧存储引擎（Storage Engine）实际读写数据（InnoDB/MYISAM 等）
  * ⑨结果合并/排序/聚合等服务器端处理
  * ⑩返回客户端并结束/事务处理/锁释放
1. 客户端发送SQL请求，连接层建立连接并验证权限。
2. 服务层解析SQL、生成执行计划，调用存储引擎接口执行操作。
3. 存储引擎操作磁盘文件获取数据，通过服务层返回给客户端，连接关闭或放回线程池。

## 二、存储引擎底层实现
### （一）InnoDB 核心原理
1. 事务支持：通过redo log和undo log保障ACID特性，聚簇索引组织表数据。
2. 锁机制：默认行级锁，基于索引实现，无索引时降级为表级锁，支持意向共享锁（IS）、意向排他锁（IX）。
3. MVCC：通过每行数据的隐藏列（DB_TRX_ID、DB_ROLL_PTR）构建版本链，结合Read View判断数据可见性，实现非锁定读。

### （二）MyISAM 核心原理
1. 无事务支持，依赖表级锁（共享锁S、排他锁X），读写操作互斥。
2. 数据与索引分离存储，采用非聚簇索引，索引叶子节点存储数据物理地址。
3. 支持全文索引，但崩溃后恢复能力弱，不适合高并发写入场景。

### （三）存储引擎选型底层依据
1. 高并发读写、事务需求：优先InnoDB，依赖其行级锁和事务日志机制。
2. 只读场景、查询频繁：可选用MyISAM，表级锁开销低，查询性能占优。

## 三、索引底层实现
### （一）B+树索引核心结构
1. 树结构：平衡多路查找树，叶子节点通过双向链表连接，非叶子节点仅存储索引键和指针。
2. 聚簇索引：InnoDB主键索引，叶子节点存储完整数据行，表数据按聚簇索引有序排列。
3. 二级索引：非主键索引，叶子节点存储主键值，查询需通过主键回表（覆盖索引可避免回表）。

### （二）哈希索引特性
1. 基于哈希表实现，等值查询速度极快，但不支持范围查询、排序。
2. InnoDB自适应哈希索引：自动为频繁访问的索引构建哈希索引，提升查询效率。

### （三）索引高效查询逻辑
1. 从根节点开始，通过索引键比较定位子节点，逐层向下遍历。
2. 叶子节点双向链表支持范围查询，无需回溯上层节点，提升查询效率。

## 四、事务与并发控制底层
### （一）事务ACID特性实现
1. 原子性（Atomicity）：依赖undo log，事务失败时通过undo log回滚数据至事务前状态。
2. 一致性（Consistency）：由原子性、隔离性、持久性共同保障，确保数据从一个一致状态切换到另一个一致状态。
3. 隔离性（Isolation）：通过锁机制和MVCC实现，避免并发事务相互干扰。
4. 持久性（Durability）：依赖redo log，事务提交后将数据变更写入redo log，即使崩溃也可通过redo log恢复。

### （二）隔离级别底层实现
1. 读未提交（Read Uncommitted）：无隔离机制，直接读取未提交数据，存在脏读。
2. 读已提交（Read Committed）：每次查询生成新的Read View，只能读取已提交数据，解决脏读，存在不可重复读。
3. 可重复读（Repeatable Read）：事务启动时生成Read View，全程复用，解决不可重复读，InnoDB默认级别。
4. 串行化（Serializable）：通过表级锁强制事务串行执行，解决所有并发问题，但性能最低。

### （三）锁机制底层逻辑
1. 行级锁：基于索引加锁，锁定索引对应的行数据，粒度细，并发度高。
2. 表级锁：锁定整张表，粒度粗，开销小，适用于读写比例悬殊场景。
3. 意向锁：为表级锁与行级锁兼容设计，避免行锁与表锁冲突，不直接阻塞数据操作。

## 五、日志系统底层原理
### （一）redo log
1. 作用：确保事务持久性，记录数据页的物理变更（如“页号XXX的偏移量YYY修改为ZZZ”）。
2. 写入机制：采用循环写方式，空间不足时覆盖旧日志，事务提交时将redo log刷盘（可通过innodb_flush_log_at_trx_commit控制刷盘策略）。
3. 崩溃恢复：重启时通过redo log重做已提交但未写入数据文件的变更。

### （二）undo log
1. 作用：支持事务回滚和MVCC，记录数据修改前的旧值（逻辑日志，如“插入了ID=1的行”对应“删除ID=1的行”）。
2. 存储方式：与数据同存于表空间，通过DB_ROLL_PTR指针串联形成版本链。
3. 回收机制：当版本链数据不再被任何事务引用时，后台线程（purge）回收undo log空间。

### （三）binlog
1. 作用：记录所有数据变更（DDL、DML），用于主从复制和数据恢复，属于逻辑日志。
2. 写入机制：事务提交时写入，支持STATEMENT（记录SQL语句）、ROW（记录数据行变更）、MIXED（混合模式）三种格式。
3. 主从复制核心：主库将binlog发送给从库，从库解析binlog并重放，实现数据同步。

### （四）slow query log
1. 作用：记录执行时间超过long_query_time（默认10秒）的SQL语句，辅助定位慢查询。
2. 实现逻辑：通过计时判断SQL执行时长，满足条件时记录SQL语句、执行时间、锁等待时间等信息。

## 六、数据存储底层结构
### （一）表空间机制
1. 共享表空间：所有表共用一个或多个ibdata文件，存储数据、索引、undo log等，适用于小数据量场景。
2. 独立表空间：每张表对应.frm（表结构）、.ibd（数据和索引）文件，便于管理和迁移，InnoDB默认启用。

### （二）数据页结构
1. 基本属性：默认16KB大小，包含页头（页类型、页号）、页体（数据行）、页尾（校验和）等部分。
2. 页组织：数据行按聚簇索引顺序存储，页内通过槽（Slot）快速定位数据行，页满时触发页分裂，空闲空间过多时触发页合并。

### （三）行格式
1. Compact行格式：将数据分为记录头信息和列数据，支持NULL值压缩、变长字段长度存储。
2. Dynamic行格式：优化大字段存储，将大字段数据完全存储在溢出页，行记录仅保留指针，适用于大文本、大二进制数据场景。
